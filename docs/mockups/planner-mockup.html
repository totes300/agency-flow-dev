Planner — who works on what, and when

A people-first timeline in the Toggl Plan mold: rows are teammates, columns are days, and a task is a bar you drag into place. It reuses the Workday grid's skeleton and visual language — Workday shows what happened, Planner shows what should happen.

This mockup is live. New in v3: task drawer on click, filters, two-line bars, and live lane reflow while dragging.

Why this view, not a day-column Kanban

Recommended

People × days timeline

Multi-day tasks are native — a bar just spans. Capacity is visible per person per day. And it mirrors the Workday grid you already ship, so the plan-vs-actual pairing is one mental model, not two.

Rejected

Kanban with days as columns

A card lives in exactly one column, so a three-day task must be duplicated, faked with spans, or squeezed to one day. It also hides who is overloaded — the one thing a planner exists to show.

Data model: a separate planSegments table

Don't put planned dates on the task itself. The plan is a relation, not a task field:

planSegments: defineTable({
  orgId: v.string(),
  taskId: v.id("tasks"),
  userId: v.id("users"),        // one segment = one person's bar
  startDate: v.string(),        // "YYYY-MM-DD", same convention as timeEntries
  endDate: v.string(),          // inclusive
  createdAt: v.number(),
  updatedAt: v.number(),
})
  .index("by_orgId_userId_startDate", ["orgId", "userId", "startDate"])
  .index("by_orgId_taskId", ["orgId", "taskId"])
  • One task, many segments. Splitting a task across weeks or people is just extra rows — no duplication.
  • Deleting a plan never touches the task. Unscheduling is a segment delete; the task keeps its status, assignees, and history.
  • Bar color = work category color (workCategories.color via getCategoryColor()) — the same tint formula as the Workday boxes and CategoryBadge. No new color field, and the Planner reads consistently with the rest of the app.
  • dueDate stays what it is — a deadline; it powers the Due filter and shows in the drawer, renderable later as a marker on the bar.
  • MVP-stage dummy data means the table can be added directly — no migration needed.

One task, many sittings — splitting without duplicating

The common reality: you start a task, get interrupted, and pick it up again a week later — sometimes with a different person. The segment model handles this exactly the way you need:

  • A bar is a reference, not a copy. Every segment points at the same taskId, so the timer, comments, links, subtasks, and time entries all accumulate in one place — the task. Click any bar and the drawer proves it: one task, all its sittings listed together.
  • ⌥-drag to split (Toggl Plan's gesture): hold Option while dragging a bar and you drop a continuation of the same task wherever you release. Or just drag the same task from the panel again — each drop adds another sitting.
  • Part badges + sibling highlight. Split tasks show 1/2, 2/2… on their bars, and hovering or selecting one outlines its siblings.

The Tasks panel and filters — planning from your real backlog

  • Built for hundreds of tasks: newest first. A flat list ordered by creation date, descending — the tasks you just captured are at the top, ready to place. No grouping ceremony; search and filters do the narrowing.
  • Cards say what matters: task + client. Title on top, client below, category as the colored dot. No estimate line — that field isn't filled in practice, so it earns no pixels.
  • Filters are panel-scoped. Project, client, category, due date (overdue / next 7 days / none) narrow the picker, never the timeline — the board always shows the whole team's real plan. Stored in URL params via nuqs so a filtered picker survives refresh.
  • Unscheduled by default. The default tab is the to-plan inbox; the toolbar badge is its count. The All tab keeps every task reachable for adding another sitting.

Creating tasks without leaving the Planner

  • Draw on empty days. Press and drag across empty cells in a person's row: a bar sketches out day-by-day, and on release a small popover asks for the title and project. Enter creates the task and its segment in one motion — try it above.
  • + New task opens a quick-add composer at the top of the panel (title + project); the task lands unscheduled, at the top of the list, ready to drag. Enter keeps the composer open for rapid capture.
  • In the real build both paths call the existing tasks.create mutation with the same defaults as the /tasks inline add (default status, no category), plus a planSegments.create when drawn onto the grid.

Execution plan (four slices)

  1. Read-only grid. planSegments schema + api.planner.weekGrid query mirroring convex/workday.ts. New route /planner, components in components/planner/, lane-packing + date math in lib/planner.ts. Seed segments (including a split task) to verify rendering, clipping at range edges, part badges, today tint.
  2. Drag: move, resize, reassign. The feel target is what this mockup now does: everything snaps to whole days (segments are date-granular — half days don't exist in the data, so the UI never suggests them), and neighbouring bars reflow into lanes live during the drag. Two viable stacks, decided at implementation time with fresh Context7 docs: (a) custom pointer events + motion (already installed) for the reflow/settle animation, or (b) dnd-timeline — headless, dnd-kit-based rows/spans/resize/snap. Either way: optimistic Convex updates with rollback-on-error toasts. Avoid packaged Gantt widgets (Bryntum, Syncfusion, react-calendar-timeline) — commercial or aging, and they'd fight the design system.
  3. Tasks panel, filters, splitting. Searchable, project-grouped panel with Unscheduled/All tabs; filter row (project, client, category, due) in URL params; drag-to-schedule with remaining-estimate default; ⌥-drag duplication; part badges and sibling highlight. This slice is the daily-driver loop: open Planner Monday morning, drain the Unscheduled tab.
  4. Polish. Week/2-week zoom, weekend toggle (Workday already has one), capacity heat in the rail, dueDate markers on bars, content-aware skeleton.

What gets reused

  • Grid skeleton — the 200px + repeat(days, 1fr) layout, sticky rail, today tint (color-mix with --primary) from components/workday/.
  • Task detail drawer — clicking a bar opens the existing task drawer/modal from components/tasks/, extended with a "Plan" section listing the task's segments. One task surface everywhere in the app.
  • Visual language — category tint formula (color-mix ~13–15% background, ~52–72% text), CategoryDot, CategoryBadge, UserAvatar.
  • Conventions — YYYY-MM-DD date strings like timeEntries, week-picker component, member filter, URL-persisted filters via nuqs.
